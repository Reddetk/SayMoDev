# BC#1: Identity and Access Management

Responsibility: User registration, authentication, session management, and token lifecycle.
Single source of truth for identity. All other BCs validate tokens independently -
BC#1 does not act as a gateway proxy.

**PACELC model: PC/EC**

- Partition: choose Consistency - authentication decisions must be correct, not available under split-brain
- Else: choose Consistency - revocation must propagate reliably; stale "valid" is a security risk,
  not an availability degradation

**Core model:** stateless payload (self-contained JWT) + stateful revocation (jti blacklist + account rev).
Stateless token enables distributed validation without calling BC#1 on every request.
Stateful revocation enables immediate invalidation before token expires.

**Common data flows:** see EventDataFlow.md (T1, T2 templates)

## Core Responsibilities

- Register accounts via email/password or Google OAuth2
- Authenticate via credentials or federated identity
- Issue RS256 JWT access tokens (self-contained, 30-day fixed expiry)
- Maintain JWT revocation store (jti blacklist + account rev)
- Lock and unlock accounts (admin-initiated or automatic on brute-force)
- Password reset and email change with OTP verification
- Publish authentication lifecycle events to Kafka via outbox
- Maintain append-only audit trail (3-year retention, compliance)
- Enforce independent JWT validation in every downstream BC (defense in depth)
- Manage multi-device sessions (max 5 concurrent per account)
- Implement RBAC: patient, relative, administrator

## Ubiquitous Language

| Term | Definition |
| ------ | ----------- |
| Account | User identity record - registration holder |
| Role | Access permission set: `patient` \| `relative` \| `administrator` |
| google_uid | Google account's unique identifier (claim `sub` from Google ID token). Stored alongside `email` in accounts table. Stable even if user changes their Google email. |
| OAuthProvider | External federated identity service (Google). Used for registration/login without password. |
| FederatedIdentity | An account linked to an external OAuth provider. Has `password_hash = NULL`; cannot authenticate via email/password until password is set. |
| code_verifier | Random string (43–128 chars) generated by frontend for PKCE. Sent to callback; Google verifies it against `code_challenge`. |
| code_challenge | BASE64URL(SHA256(code_verifier)). Sent to Google in authorization request to prove frontend identity. |
| Session | Active authenticated connection bound to a device fingerprint |
| JWT | Self-contained RS256-signed credential token |
| Access Token | JWT with fixed 30-day expiry. Not sliding - `exp` is immutable after signing |
| jti | UUID claim - unique per-token identifier; individual token blacklist key |
| rev | Integer claim - account revision; increment invalidates all tokens where `token.rev < account:rev` |
| kid | JWT header field - identifies signing key; enables key rotation without mass-invalidation |
| Token Blacklist | Set of revoked `jti` values: L2 Redis (cache) + L3 PostgreSQL (source of truth) |
| PasswordHistory | Last 5 bcrypt hashes per account; reuse prevention |
| Device Fingerprint | Derived from User-Agent + client hints; session binding |
| last_activity | Last API call timestamp - eviction ordering only, NOT token validity extension |
| JWKS | Public key endpoint; all services resolve signing keys by `kid` |

## Bounded Context Invariants

### 1. Account Uniqueness Invariant

- Email is globally unique across all accounts
- Duplicate registration returns identical response regardless of whether email exists
  - **why**: attacker must not be able to discover registered emails via registration endpoint

### 2. Password Policy Invariant

- Password stored as bcrypt hash (cost 12); plaintext never persisted anywhere
- Minimum 8 characters
- bcrypt input capped at 72 bytes - inputs exceeding this MUST be rejected, never silently truncated
  - **why**: bcrypt silently ignores bytes beyond 72, making "password" and "password" + 100 extra bytes
    hash to the same value; silent truncation creates false password equivalence
- Password history: last 5 hashes; reuse rejected via bcrypt.Compare per stored hash
  - **why hash comparison, not byte equality**: bcrypt generates a unique random salt on every call,
    so hash("pwd") != hash("pwd") even for identical passwords; byte comparison always rejects valid passwords
  - O(5) bcrypt operations ≈ 1–2s at cost 12; acceptable only on write path, never read path

### 3. Token Model and Lifecycle Invariant

**Fixed-expiry token (no sliding window)**

```
exp = iat + 30 days  <- absolute, immutable at issuance
```

**Why no sliding window**: self-contained tokens cannot have `exp` mutated after RS256 signing
without invalidating the signature. Sliding expiry requires re-signing on every request -
defeats stateless JWT purpose and creates unacceptable per-request signing overhead.

`last_activity` role: updated async on each request, used exclusively for eviction ordering.
Does NOT extend `exp`. Token validity is determined solely by `exp` claim.

**Token claims:**

```
Header:
  alg: RS256
  kid: <key-identifier>   <- required; enables key rotation

Payload:
  iss:        urn:saymo:identity-service
  sub:        <account_id> (UUID)
  aud:        api.saymo
  role:       patient | relative | administrator
  exp:        iat + 2592000s (30d, fixed at issuance)
  iat:        <unix timestamp>
  jti:        <UUID v4>   <- unique per token; blacklist key
  session_id: <UUID>      <- links token to session record
  rev:        <integer>   <- account revision at issuance; mass-revoke key
```

**jti uniqueness**: UUID v4 collision ~10⁻¹⁸; UNIQUE DB constraint enforces; retry up to 3x on collision;
alert if any collision occurs (should never happen).

**Key rotation**: every JWT includes `kid`; services validate tokens signed by current and previous key
simultaneously (overlap window ≥7 days).

### 4. Session Invariant

- Session exists only for active (non-locked, non-deleted) account
- Maximum 5 concurrent sessions per account
- On 6th login: session with oldest `last_activity` is evicted atomically in the same transaction;
  evicted token immediately blacklisted
  - **why atomic**: non-atomic eviction creates a window where 6 sessions exist simultaneously
- Session creation serialized under pessimistic lock
  - **why**: without serialization two concurrent 5→6 logins both pass the count check,
    resulting in 6 sessions despite the invariant
- Session revocation is immediate: jti blacklisted OR `rev` incremented (mass-revoke)

### 5. Rate Limiting Invariant

- 50 failed login attempts per day per account → account locked 24h
- 100 login attempts per hour per IP → 429
- **Redis-unavailable policy: fail-closed** - in-process per-instance counters with conservative threshold
  - **why fail-closed**: fail-open on rate limiting allows brute-force to proceed during Redis outage;
    conservative in-process counters are degraded but not disabled

### 6. Lock Semantics Invariant

**Both lock types (failed attempts + admin) MUST perform mass-revoke (rev++).**

**Why**: access token is valid 30 days. Lock that only blocks new logins leaves an attacker holding
a valid token authenticated for up to 30 days post-lock. Unacceptable security gap.

Lock procedure (both types):

1. Increment `rev` atomically with lock status update (same transaction)
2. Collect and blacklist all active `jti` values in same transaction
3. Delete all sessions
4. Publish lock event via outbox

`account:rev` in L2 Redis is never cached in L1 - always read fresh from L2 - so mass-revoke
takes effect at L2 immediately after the Redis write, without waiting for L1 TTL expiry.

### 7. OTP Security Invariant

All verification code comparisons MUST use constant-time comparison.

- **Why**: standard equality exits early on first differing byte - timing difference leaks
  how many leading bytes match, enabling timing attacks on 6-digit OTP codes
- Error responses MUST be generic: single message "invalid or expired code";
  never distinguish wrong code / expired / not found
  - **why**: distinguishing cases reveals code lifecycle state to attacker
- OTP plaintext NEVER written to logs, events, or outbox payloads

### 8. CORS Policy Invariant

CORS middleware MUST execute before JWT validation.

- **Why**: OPTIONS preflight carries no Authorization header; if JWT runs first,
  preflight gets 401 and CORS breaks for all browsers regardless of valid credentials

```
Production:  https://app.saymo.com only (explicit whitelist, no wildcards)
             AllowCredentials: true - wildcard origin forbidden when credentials enabled (browser spec)
Staging:     https://staging.saymo.com
Development: http://localhost:3000, http://localhost:5173
Unknown env: empty whitelist (fail-closed)
```

Rejected origin: CORS headers not added; browser blocks response; handler still executes
(server does not short-circuit on rejected origin - only browser enforcement).

## Authentication Operations

### Registration - Email/Password

Two-step HTTP contract (see API Flow section below for full details):

**Step 1: POST /iam/auth/register/verify**

- **Trigger:** client initiates registration with email
- **Pre-conditions:** valid email format
- **Anti-enumeration:** response body and timing identical regardless of whether email exists
- **Side effect:** OTP created (6-digit code; SHA256 hash stored, plaintext NOT persisted)
- **OTP TTL:** 3h
- **Response:** 200 OK { message: "Verification code sent to email" }
  - NO events published (initialization phase only)
- **Delivery:** plaintext OTP code sent via Yandex Cloud Postbox (HTTP call after DB commit, outside transaction)
  - plaintext-only body (no HTML, no links); code is the sole content of the message
  - If Postbox unavailable → 503 returned to client; OTP record already persisted → client can retry the same step
  - Integration: AWS SESv2-compatible API; endpoint `postbox.cloud.yandex.net`; auth via static key (AWS Signature V4) or IAM token (`X-YaCloud-SubjectToken`); service account role `postbox.sender`

**Step 2: POST /iam/auth/register**

- **Trigger:** client submits email, OTP code, password, role, classifier
- **Pre-conditions:** OTP not expired, email format valid, password meets policy, role valid, classifier required for patient role
- **Note on `classifier` field:** значение передаётся из browser localStorage (onboarding session), не вводится пользователем на экране регистрации. Онбординг полностью frontend-only - прогресс хранится в localStorage/sessionStorage до момента регистрации.
- **OTP verification:** constant-time comparison, generic error on mismatch (no timing leak)
- **Atomicity:** account creation + password history entry + code cleanup in single ACID transaction
  - impossible state: account without password_hash cannot exist post-commit
- **Events published (atomic):**
  - `AccountRegistered` (CANONICAL TRIGGER for BC#4/BC#2 business start)
    payload: `{ accountId, role, classifier: { difficulty, aphasiaType }, registrationMethod: "email" }`
  - `AccountEmailVerified` - аудит-маркер факта email-верификации.
    NOT required for downstream business - BC#4 и BC#2 опираются исключительно на `AccountRegistered`.
    Потеря этого события не нарушает бизнес-логику ни в одном даунстрим сервисе.
    payload: `{ accountId, verifiedAt }`
- **Session creation:** separate transaction with race guard (max 5 concurrent per account)
- **Returns:** 201 { access_token, account_id, role, session_id }
- **Error cases:**
  - 200 OK on Step 1 (always, anti-enumeration)
  - 400: policy violation, format invalid, OTP expired/used
  - 409: email already registered

### Registration - OAuth2 (Google)

**Chosen flow:** Authorization Code + PKCE (стандарт для PWA/SPA; Implicit flow устарел с 2019, RFC 6749, OAuth 2.0 BCP for browser-based apps)

**New endpoints:** `GET /iam/auth/oauth/google` + `GET /iam/auth/oauth/google/callback`

#### Full flow (8 steps)

```
[1] Frontend: пользователь нажимает [Войти через Google]
    → Frontend генерирует code_verifier (случайная строка 43-128 символов)
    → Frontend вычисляет code_challenge = BASE64URL(SHA256(code_verifier))
    → Frontend перенаправляет браузер на:
      GET /iam/auth/oauth/google
      (BC#1 формирует redirect URL к Google с параметрами)

[2] BC#1 → перенаправляет браузер на Google OAuth consent screen:
    https://accounts.google.com/o/oauth2/v2/auth
      ?client_id=<GOOGLE_CLIENT_ID>
      &redirect_uri=<https://api.saymo.com/iam/auth/oauth/google/callback>
      &response_type=code
      &scope=openid email profile
      &code_challenge=<code_challenge>
      &code_challenge_method=S256
      &state=<CSRF_token>   <- случайный, хранится в сессии или cookie
      &prompt=select_account

[3] Пользователь: авторизуется в Google, даёт consent

[4] Google → redirect браузера на:
    GET /iam/auth/oauth/google/callback
      ?code=<authorization_code>
      &state=<CSRF_token>

[5] BC#1: callback handler
    a. Проверяет state (CSRF protection - сравнение с сохранённым)
    b. Делает server-to-server запрос к Google Token Endpoint:
       POST https://oauth2.googleapis.com/token
         code=<authorization_code>
         client_id=<GOOGLE_CLIENT_ID>
         client_secret=<GOOGLE_CLIENT_SECRET>
         redirect_uri=<callback URL>
         grant_type=authorization_code
         code_verifier=<code_verifier>  <- PKCE verification
    c. Google возвращает: { id_token, access_token, refresh_token }

[6] BC#1: верификация Google ID token (server-side)
    a. Загружает Google JWKS: https://www.googleapis.com/oauth2/v3/certs
       (кэширует согласно Cache-Control, обычно 6 часов)
    b. Верифицирует RS256 подпись ID token с Google public key
    c. Проверяет claims:
       - iss: accounts.google.com или https://accounts.google.com
       - aud: <GOOGLE_CLIENT_ID>
       - exp: не истёк
       - email_verified: true  <- ОБЯЗАТЕЛЬНО
    d. Извлекает: { sub (google_uid), email, name, picture }

[7] BC#1: lookup или создание account
    CASE A - email уже есть в БД (повторный вход):
      - Найти account по email
      - Проверить account.status = "active"
      - Проверить google_uid совпадает (или привязать если впервые через Google)
      - Создать Session + выдать SayMo JWT
      - Опубликовать: SessionCreated

    CASE B - email не найден (первая регистрация через Google):
      - В ACID-транзакции:
        - Создать account { email, google_uid, password_hash=NULL, role=patient, status=active }
        - Записать в Outbox: AccountRegistered { registrationMethod: "oauth2", classifier }
      - Создать Session + выдать SayMo JWT
      - Публикует: AccountRegistered, SessionCreated

    CASE C - email найден, но аккаунт создан через email/password:
      - Привязать google_uid к существующему account
      - Продолжить как CASE A

[8] BC#1 → redirect браузера на frontend с токеном:
    → Redirect на https://app.saymo.com/auth/callback?token=<SayMo JWT>
    - или -
    → Redirect с Set-Cookie (httpOnly, Secure) если cookie-based
    Downstream BC не знают о методе входа - они видят обычный SayMo RS256 JWT.
```

#### Ключевые инварианты Google OAuth

```
1. email_verified: true - ОБЯЗАТЕЛЬНАЯ проверка до создания/входа в account
   Причина: Google допускает аккаунты с неверифицированным email.

2. state (CSRF token) - генерируется BC#1, хранится в server-side сессии
   или signed cookie (httpOnly). Сравнивается в callback.

3. Google JWKS кэшируется согласно Cache-Control заголовка.
   Fail-closed на недоступность: если JWKS недоступен → 503, НЕ пропускаем.

4. google_uid (claim "sub" из Google ID token) - уникальный идентификатор
   Google аккаунта. Хранится в accounts таблице рядом с email.
   НЕ используем email как единственный идентификатор (пользователь может сменить
   email в Google, sub остаётся тем же).

5. classifier для регистрации через Google:
   Если пользователь прошёл онбординг → classifier берётся из localStorage.
   Если без онбординга → fallback: запросить classifier после OAuth callback
   или использовать default classifier.

6. password_hash = NULL для OAuth-аккаунтов.
   Такой аккаунт не может войти через email/password пока не установит пароль.

7. Session model: ИДЕНТИЧНА email/password.
   После OAuth login - создаётся Session, выдаётся SayMo JWT с теми же claims.
   Downstream BC не отличают OAuth сессию от password сессии.

8. Blacklist / Revoke: ИДЕНТИЧНЫ email/password.
   OAuth refresh_token от Google НЕ хранится в SayMo (не нужен - SayMo
   использует свой JWT lifecycle, не Google tokens).
```

**Pre-conditions:** valid Google ID token, `email_verified: true`
**Why `email_verified` is mandatory:** Google allows accounts with unverified emails;
accepting them would let attacker register with someone else's email before owner verifies it

**Atomicity:** account creation in single transaction; `password_hash = NULL`

**Publishes:** `AccountRegistered` (payload: `{ registrationMethod: "oauth2", accountId, role, classifier: { difficulty, aphasiaType } }`)

**Returns:** `{ access_token, account_id, role }` via redirect

#### Step 2: Registration Completion

```
POST /iam/auth/register
Content-Type: application/json

{
```

### Login - Email/Password

**Pre-conditions:** account active, rate limits not exceeded

**Rate limit order:** IP check → account lookup → account rate check

- **why IP first**: account lookup itself reveals timing difference; IP check before lookup
  prevents using login as account existence oracle

**Timing safety:** non-existent account runs bcrypt.Compare against dummy hash

- prevents timing difference between "wrong email" and "wrong password"

**Session atomicity:** session creation + optional eviction serialized under pessimistic lock

**Publishes:** `SessionCreated`

**Returns:** `{ access_token }`

**Error cases:** 401 generic always; 429 on rate limit

---

### Logout

**Pre-conditions:** valid JWT

**Guarantees:** jti blacklisted in Redis L2 immediately; session deleted; ≤60s L1 window remains

- **why ≤60s acceptable**: L1 is per-process and TTL-bounded; mass-revoke uses rev++ which bypasses L1

**Publishes:** `AccessTokenRevoked`, `SessionTerminated`

**Returns:** 204 No Content

---

### Password Reset (unauthenticated)

**Pre-conditions:** none

**Anti-enumeration:** identical flow (code path, timing, response) regardless of email existence

**OTP:** 6-digit numeric code; SHA256 hash stored; expires 3h; constant-time comparison

- unified generator per ADR-006; bruteforce mitigated by rate limiting (§5: 50 attempts/day per account + 100 req/hour per IP)

**Atomicity:** password update + rev increment + session mass-delete + jti collection in one transaction

- **why atomic**: gap between password update and session revoke leaves old tokens valid with new password

**Post-reset:** actor must re-authenticate; all existing sessions invalidated

**Publishes:** `AccountPasswordResetRequested`, `AccountPasswordResetCompleted`, `AccessTokenRevoked ×N`

---

### Password Change (authenticated)

**Pre-conditions:** current password verified, new password meets policy, not in last 5 passwords

**History check:** bcrypt.Compare per stored hash, not byte equality - O(5) operations under account lock

- **why not byte equality**: bcrypt random salt means identical passwords produce different hashes

**Atomicity:** password update + history update + rev increment + session mass-delete in one transaction

- **why history in same transaction**: concurrent password changes could corrupt history without account lock

**Post-change:** actor must re-authenticate

**Domain method signature:** `ChangePassword(newHash string) (revokedJTIs []string, err error)`

- returns collected jti slice for immediate Redis blacklist write (G9 Revocation Write Order)
- consistent with `Lock` and `SoftDelete` which also return `revokedJTIs`
- see ADR: ChangePassword T4 Mass-Revoke Return Contract below

**Publishes:** `AccountPasswordChanged`, `AccessTokenRevoked ×N`

---

### Email Change (authenticated)

**Pre-conditions:** new email not registered, current session valid

**OTP sent to NEW address** - proves ownership of new email before committing change

- sending to old address would allow change to email the user no longer controls

**Atomicity:** email update + rev increment + session mass-delete in one transaction

**Post-change:** actor must re-authenticate

**Publishes:** `AccountEmailChangeRequested`, `AccountEmailVerifiedForChange`, `AccessTokenRevoked ×N`

---

### Account Lock / Unlock (admin)

**Lock:** rev++ + all jti blacklisted + sessions deleted atomically - see Lock Semantics §6

**Unlock:** status=active; does NOT issue new token; actor must re-login

**RBAC:** requires `token.role = administrator`
**Audit:** `audit_log.actor_id = token.sub` - admin identity from JWT claims, never from request body

**Publishes:** `AccountLockedByAdmin` / `AccountUnlocked`

## Token Validation Flow

Executed by EVERY microservice on EVERY request.
Gateway pre-checks do NOT replace this - each service is an independent trust boundary.

```
Step 1 - Signature
  Parse kid from JWT header
  Resolve RS256 public key from local JWKS cache (TTL 1h)
  Unknown kid → ONE fetch from IAM /jwks.json (timeout 2s, no retry) → fail-closed on failure
  Why fail-closed: allowing unresolvable kid would permit attacker to forge tokens
  with an arbitrary self-generated key

Step 2 - Claims (±30s clock skew tolerance)
  exp, iat, iss, aud
  Why before revocation: checking revocation on tampered/expired token wastes cache/DB resources

Step 3 - Revocation: L1 → L2 → L3
  L1 in-process (TTL 60s):
    HIT blacklisted → 401
    HIT valid       → proceed to Step 4
    MISS            → L2

  L2 Redis:
    Unavailable           → skip to L3; log WARN
    jwt:black:<jti>       → 401
    account:rev > token.rev → 401
    L2 miss               → L3 (Redis is cache, PostgreSQL is truth)
    OK                    → cache positive in L1; proceed

  L3 PostgreSQL (on Redis unavailable OR L2 miss):
    jwt_blacklist + accounts.rev
    Log WARN; increment l2_miss_l3_hit_total
    Alert on sustained growth → Redis memory pressure

Step 4 - RBAC + Ownership
  Admin endpoints:  token.role = administrator → else 403
  Patient data:     query with account_id filter → empty result → 404 (not 403)
  Why 404 not 403:  403 reveals resource exists; 404 prevents enumeration (IDOR prevention)
```

---

## Blacklist Write Order

**Chosen model: Redis-first, PostgreSQL via outbox (async durable)**

```
On revoke:
  1. Write Redis L2 first       → immediate effect for all L2 readers
  2. Write outbox in same DB TX → async sync to L3 PostgreSQL

Tradeoff accepted:
  Crash between Redis write and DB COMMIT → Redis entry exists, L3 does not
  Mitigation: outbox is in same TX as business operation; if TX commits, outbox row exists;
  async processor syncs both L3 and Redis from outbox

Redis unavailable during revoke:
  Skip Redis write; log ERROR; outbox TX still commits
  Token validation falls through to L3 on L2 miss
  Alert fires immediately on redis_write_failure_total > 0
```

`account:rev` never cached in L1 → always read fresh from L2 → mass-revoke via rev++
effective immediately at L2, without waiting for 60s L1 expiry.

## Caching Strategy

```
L1 - In-Process (sync.RWMutex + LRU)
  Capacity:     10 000 entries
  TTL:          60s
  Stores:       jti blacklist hits, positive valid-token results
  Race window:  ≤60s stale valid result after jti-based revocation
  Mitigation:   mass-revoke via rev++ bypasses jti L1; account:rev always read fresh from L2

L2 - Redis (IAM-dedicated) - cache, NOT source of truth
  jwt:black:<jti>           TTL = token remaining TTL
  account:rev:<account_id>  TTL = 30 days (refreshed on rev update)
  session:<session_id>      TTL = token exp
  rl:account:<id>:day       TTL = 86400s
  rl:ip:<ip>:hour           TTL = 3600s
  Write: Redis first; L3 via outbox
  On miss: always fall through to L3

L3 - PostgreSQL (source of truth)
  Consulted: Redis unavailable OR L2 miss
  Alert: l2_miss_l3_hit_total sustained growth → Redis memory pressure
```

## Key Rotation Policy

Frequency: every 90 days or on compromise

```
1. Generate new key pair; assign new kid
2. Add to k8s secret alongside current key (both active)
3. Rolling restart IAM pods
4. Wait ≥7 days  <- JWKS cache TTL propagation across all services
                   Why: services cache JWKS for 1h; need full propagation before switching signing
5. Switch signing to new key
6. Wait 30 days  <- max token lifetime; old-key-signed tokens expire naturally
7. Remove old key from secret

Overlap window: ≥7 days - both keys in JWKS simultaneously
Cleanup window: 30 days - old key stays in JWKS until all tokens signed by it have expired
```

Alert: `jwks_active_keys_count != 2` during rotation window

## Dependencies

**External:**

- Yandex Cloud Postbox - OTP and password-reset email delivery
  - **Integration:** AWS SESv2-compatible API; endpoint `postbox.cloud.yandex.net`
  - **Auth:** static access key (AWS Signature V4) or IAM token (`X-YaCloud-SubjectToken`); service account with `postbox.sender` role
  - **Domain verification:** DKIM TXT record required in DNS before first send (ops prerequisite, not runtime)
  - **Call timing:** HTTP call after DB commit - OTP/reset record already persisted when call is made
  - **Failure policy:** Postbox unavailable → 503 to client; OTP in DB survives; client retries POST /register/verify or POST /auth/password-reset
    - NOT silent success (anti-enumeration applies to response shape, not to delivery failure)
  - **Bounce / stop-list:** Postbox permanently blocks delivery to addresses that returned a hard bounce (SMTP 5xx). If user's email is in stop-list → OTP delivery silently fails at transport layer. BC#1 receives no callback; treat as Postbox unavailability → 503. Operational monitoring via Yandex Data Streams notification stream (`eventType: "Bounce"`) - separate ops concern, not in request path
  - **Notifications (QoS 1):** Postbox emits `Send` / `Delivery` / `Bounce` / `DeliveryDelay` events to Yandex Data Streams - consumed by ops/monitoring only, not by BC#1 runtime
- Google JWKS - OAuth2 ID token validation; cached per Cache-Control header (typically 6h); fail-closed on unavailability: if JWKS unreachable → 503, never pass-through

**Internal (event-driven only, no sync calls):**

- Produces to: `saymo.identity.events`
- BC#1 is a leaf producer - subscribes to no other BC

**Downstream consumers:**

- BC#2 consumes: `AccountLockedByAdmin`, `AccountLockedByFailedAttempts`, `AccountUnlocked`
- BC#4 consumes: `AccountRegistered` (auto-activate initial program)

## Guarantees

```
Idempotency:    OTP verification: exactly-once via verification_codes table
                Revocation: idempotent - blacklisting already-blacklisted jti is safe
                Session creation: serialized under pessimistic lock

Ordering:       Kafka partition key = account_id - all events for one account ordered

Revocation SLO: jti-based: effective within ≤60s (L1 TTL)
                rev-based (mass-revoke): effective immediately at L2 (account:rev not in L1)

Availability:   Redis unavailable → rate limiting fail-closed (degraded, not disabled)
                                  → token validation falls through to L3 (no outage)
                Postbox unavailable → registration/reset blocked; 503 returned; no silent pass

Timing safety:  All anti-enumeration paths: identical code, identical response, identical timing
CORS:           Fail-closed on unknown environment → empty origin whitelist
JWKS:           Fail-closed on unresolvable kid → 401, never pass-through
```

## Architectural Decisions

### ADR: ChangePassword T4 Mass-Revoke Return Contract

**Status:** Accepted

**Context:**

Domain methods `Lock(until *int64)` и `SoftDelete()` на агрегате `Account` выполняют T4 Mass-Revoke:
сбрасывают все сессии и возвращают `[]string` собранных `jti` для немедленной записи в Redis (G9 Revocation Write Order).

Метод `ChangePassword(newHash string) error` также является T4 Mass-Revoke операцией
(password update + rev++ + session mass-delete в одной транзакции, согласно §Password Change),
однако его сигнатура возвращала только `error`. Это создавало несоответствие:
application service не мог получить список `jti` из доменного метода и был вынужден
либо читать сессии до вызова метода (лишний запрос), либо не выполнять немедленную Redis-запись.

**Decision:**

Изменить сигнатуру доменного метода `ChangePassword` на:

```go
func (a *Account) ChangePassword(newHash string) (revokedJTIs []string, err error)
```

Метод внутри вызывает `a.RevokeAllSessions()` и возвращает собранные `jti` вместе с результатом
операции. Application service использует возвращённые `jti` для записи в Redis L2 согласно G9.

**Consequences:**

- Сигнатуры всех T4 Mass-Revoke методов агрегата теперь единообразны:
  - `Lock(until *int64) (revokedJTIs []string, err error)`
  - `SoftDelete() (revokedJTIs []string, err error)`
  - `ChangePassword(newHash string) (revokedJTIs []string, err error)`
- Application service для `ChangePassword` (E15) получает `jti` без дополнительных запросов к БД
- Инвариант §6 Lock Semantics ("collect and blacklist all active jti in same transaction")
  распространяется явно на смену пароля через доменный контракт, а не только через описание операции
- Коллбеки через `PasswordResetConfirm` (E6) используют ту же схему

**Scope:** domain layer only - изменение не затрагивает HTTP-контракты, события Kafka или схему БД.

## Архитектура

Сервис построен по принципам Hexagonal / Clean Architecture:

- `cmd` -  точка запуска identity-service (BC#1).

- `internal/core` - доменная бизнес-логика (AuthService, AccountService, SessionService, TokenService, OTPService)
- `internal/adapter/primary/http` - входящие HTTP-адаптеры (handlers, middleware: JWT, observability, CORS)
- `internal/adapter/secondary` - исходящие адаптеры (PostgreSQL, Redis, Kafka outbox)

- `migrations` - SQL-миграции базы данных
- `mocks` - сгенерированные моки для тестов
